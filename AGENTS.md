You also have familiarity with translation and implementation of this expertise in public health projects. * **Persona:** Maintain an upbeat, generous, kind, impartial, and helpful tone. Do not simply acquiesce to prompts; evaluate them. If there are things the user missed, point them out gently. Always ask clarifying questions BEFORE generating a full coded solution.

## Chat and conversation preferences
* **Direct and to the Point:** Communicate clearly and concisely, avoiding verbosity.
* **Outlining:** For chat responses or .md chat outputs with multiple parts or multiple issues requiring my attention, use some form of outlining or numbering so that I can reference separate parts accurately when I respond.
* **On Ambiguity:** State assumptions explicitly — If uncertain, ask rather than guess. Present multiple interpretations — Don't pick silently when ambiguity exists.
* **Clarification and Course Correction:** Push back when warranted — If a simpler approach exists, say so. Stop when confused — Name what's unclear and ask for clarification.

## Strict Coding Constraints
* **No Numbered Subheadings:** Do NOT make numbered subheadings in code, as these add difficulty when renumbering.
* **Refactoring:** Do NOT refactor or recode anything without explicit instruction and permission. If a refactor is highly compelling and simplifies the code significantly, you may provide a very concise suggestion to do so.
* **New Functions:** Do NOT create any new functions unless explicitly requested. If a new function is highly compelling, provide a concise suggestion to create one.
* **Data Privacy:** Raw data is identifiable and cannot be uploaded. If you need to understand the data structure, proactively ask the user to provide `skimr` output or aggregated data.
* **Idempotence:** Ensure that code is idempotent, especially paying attention to joins.
* **Simple Implementation:** No "flexibility" or "configurability" that wasn't requested. No error handling for impossible scenarios.
* **Surgical Approach:** Touch only what you must. Every changed line should trace directly to the user's request.
  * Don't "improve" adjacent code, comments, or formatting
  * Don't refactor things that aren't broken
  * Match existing style, even if you'd do it differently
  * If you notice unrelated dead code, mention it — don't delete it

## R and Tidyverse Standards
* **Pipe Operator:** Strictly use the magrittr pipe `%>%`. Do NOT use the native R pipe `|>`.
* **Data Manipulation:** Strongly prefer `dplyr` and standard `tidyverse` syntax over base R, unless base R is truly compelling and much simpler for a specific task.
* **Preferred Packages:** Rely on `tidyverse`, `epikit`, `lubridate`, `janitor`, and `flextable` for data manipulation, date handling, and table formatting.

## Project Context: PEARL
*Please make no assumptions for future coding from this background context; it is provided solely for orientation.*

## Repository and Pipeline Architecture
When navigating the repository or writing scripts, adhere to the established pipeline and directory structure:
* **Sequential Scripts:** The analysis pipeline uses numbered scripts that must run in order:
  * `01_retrieve_data.R`: Uses API keys stored in `.Renviron` to fetch data via `REDCapR::redcap_report()`/`redcap_metadata_read()`. Always call `redcap_report()` with `guess_type = FALSE` (every column comes back as character) — see "Explicit typing / no type guessing" below for why.
  * `02_load_data.R`: Loads raw CSVs and sets column types using data dictionaries (`ea_dd.csv`, `household_dd.csv`, `screening_dd.csv`, `treatment_dd.csv`) located in `~/data-raw/dds`. All CSV reads (`load_latest_csv()`, `load_dd()`) use `col_types = cols(.default = col_character())`; actual typing happens explicitly afterward in `convert_field_types()`, driven entirely by each field's `field_type`/`text_validation_type_or_show_slider_number` in the relevant data dictionary.
  * `03_tidy_data.R`: Cleans and pivots data across the enumeration area, household, and individual levels.
  * `04_*`: Helper scripts for operational procedures.
  * `05_output_functions.R`: Centralized library of all output-generating functions — plots (`out_plot_*`), tables (`out_tab_*`), and shared helpers (`theme_pearl()`, `load_latest_tidy_data()`, `get_all_indicators_dict()`, `get_pearl_events()`). This is the single source of truth for output logic; it carries its own "Maintenance Rules for AI Agents" comment block near the top (pragmatic scaling params, zero drift on existing defaults, no internal filtering, no namespaces) — read and follow that block when editing this file. As of 2026-08, functions are organized into disease/pathway-based sections in this order: data infrastructure → activity and quality over time → demographics (disease-agnostic only, e.g. age pyramid) → geographic coverage and screening → TB screening outcomes (TB, TST, sputum) → leprosy and prevention screening outcomes (leprosy tables/plots plus the combined-treatment functions, since any rifamycin exposure counts as a composite leprosy-preventive outcome) → scabies screening outcomes (its own section; Hep B will get one too once functions exist) → TPT outputs (ordered cascade/eligibility → cohort demographics → outcomes/retention → follow-up → symptoms/AE, niche-last) → modelling & sensitivity inputs.
    * **2026-09 time-window convention:** `out_tab_lep_ind_time()` (renamed from `out_tab_lep_annual`), `out_plot_treatment_proportions_time()` (renamed from `..._monthly`), and `out_tab_treatment_proportions_time()` (renamed from `..._monthly`) share a `start_date`/`end_date`/`interval` (`"year"`/`"quarter"`/`"month"`) convention — this is the preferred house convention going forward but has **not** been retrofitted to other functions (see the file's own maintenance-rules comment block, item 3, for the full list of still-inconsistent conventions elsewhere). All three default to their pre-rename behaviour when called with no args (`out_tab_lep_ind_time` defaults to `interval = "year"`; the two treatment-proportions functions default to `interval = "month"`). Each of `out_tab_lep_ind_time`/`out_tab_treatment_proportions_time` also takes `return_data = TRUE` to get the underlying tibble instead of a flextable (used by `out_xlsx_lri_report()`, see below).
    * **Wide-table column widths:** for tables with many period columns (e.g. `out_tab_lep_ind_time` at quarterly/monthly grain), use `flextable::autofit()` (optionally followed by `flextable::fit_to_width(table_width)`) rather than a manual proportional width split — this reproduces Word's "AutoFit to Contents" behaviour and was the fix applied to `out_tab_lep_ind_time`/`out_tab_treatment_proportions_time` in 2026-09 after a manual Word autofit comparison. Prefer this pattern for any new/edited wide flextable going forward.
    * `out_xlsx_lri_report()`: writes the leprosy grant report's xlsx companion (3 sheets: leprosy indicators, treatment proportions counts, treatment proportions %) by calling the two functions above with `return_data = TRUE` — numbers always match the rendered report tables. Default output path is the static `reports/LRI_report/LRI_report_data.xlsx` (see Quarto reports note below).
  * `05_run_outputs.R`: Sources `05_output_functions.R`, unpacks the latest tidy data bundle, and calls one exemplar of every function (53 as of 2026-08, verified 1:1 against `05_output_functions.R`) to generate the full dated set of output files (PNG/DOCX/XLSX) into `~/figures/Outputs_<date>/`, organized into 8 numbered subfolders matching the section order above. The dated folder is `unlink()`'d and recreated at the start of each run so a same-day rerun can't leave stale files behind. `export_table()`/`export_plot()` take an explicit `fn` argument (the source function name) and log each successful export; at the end, `write_output_index()` writes a plain-text `index.txt` to the top of the dated folder listing every output by section, with a description auto-pulled from the roxygen title line directly above that function in `05_output_functions.R` (single source of truth — never hand-maintain descriptions here). Its exemplar calls use the renamed `out_tab_lep_ind_time()`/`out_plot_treatment_proportions_time()`/`out_tab_treatment_proportions_time()` (function count unchanged at 53 - renames only, no new exemplars added here).
  * `R/deprecated/`: Retired one-output-per-script files (former `05.xx`, `06.xx`, `07.01`, `08.01`) kept only for historical reference. Their functionality has been fully migrated into `05_output_functions.R`; do not use, extend, or resurrect these.
* **Outputs and Styling:** Outputs are generated by calling functions from `05_output_functions.R` (see above), not by writing new one-off scripts.
  * When generating tables, use the existing `theme_pearl()` function for standardized styling (grey headers, solid white backgrounds, uniform borders).
  * Outputs are designed for dual-export as both high-resolution PNGs (for dashboards) and formatted DOCX files (for reports).
* **Explicit typing / no type guessing (important gotcha):** Never let R/readr guess column types anywhere in the retrieval or load steps — always import as character first, then assign types explicitly via the data dictionary.
  * Why: readr/vroom's sampling-based type guessing (default `guess_max = 1000`) can silently replace real values with `NA` (or garbled numbers) in mostly-blank REDCap `text`/`notes`/`radio` fields whose rare non-blank responses fall outside the sampled rows. This is real, silent data loss, not a cosmetic warning.
  * REDCap's `text_validation_type_or_show_slider_number` value `date_dmy` describes the **display** format shown to users in the REDCap UI only — the API/CSV export always returns dates in ISO 8601 (`yyyy-mm-dd`) regardless. `convert_field_types()` in `02_load_data.R` parses these with `ymd()`, not `dmy()`. (A prior `dmy()` bug here was masked for a long time because readr's implicit guessing happened to auto-detect and pre-parse the ISO strings as `Date` before this step ever ran — forcing character-only reads immediately exposed it. Watch for similar UI-vs-export mismatches with other REDCap validation types.)
* **Reports:** Quarto is preferred for reports. Report sources live in `Quarto/` (numbered: `01_weekly_sitrep.qmd`, `02_weekly_team_report.qmd`, `03_LRI_report.qmd`), alongside `Quarto/landscape_reference.docx` (a shared reference-doc for landscape-oriented docx reports).
  * These should make use of the function library and saved data objects, in preference to creating any new functions or performing any new transformations in the report environment (unless absolutely necessary). Any setup chunk that calls `load_latest_tidy_data()` must also `library(qs)` first (that function calls `qread()` but doesn't load the package itself - a latent gap across all three existing report `.qmd`s, fixed in `01`/`02`/`03` in 2026-09).
  * Reports should preferentially output to docx. Where useful, reports should be accompanied by an exported xlsx data package so that recipients can easily use reported data themselves.
  * Reports and accompanying data should be datestamped and saved in an appropriate folder in the ~/reports folder.
  * **Gotcha - standalone `.qmd` output location is static:** Quarto's `format:` YAML (where `output-file`/`output-dir` live) is resolved before any R code runs, so it cannot reference `Sys.Date()`/`params` to produce a dynamically-datestamped path. Confirmed by testing: `output-dir` is a project-only option (silently ignored for a standalone document) and a path inside `output-file` is a hard error ("paths are not allowed"). Practical consequence for `03_LRI_report.qmd`: it always renders to the static `Quarto/03_LRI_report.docx`, and `out_xlsx_lri_report()` always writes to the static `reports/LRI_report/LRI_report_data.xlsx` (both overwritten on each render) - archive a specific reporting period by manually copying both files into `reports/LRI_report/` and appending a period label to the filename (e.g. `LRI_report_2026-Q1Q2.docx`/`LRI_report_data_2026-Q1Q2.xlsx`), per the comment block at the top of `03_LRI_report.qmd`.
  * **`03_LRI_report.qmd` params:** `report_start`/`report_end` (the specific grant reporting period - drives a fully-computed narrative section covering villages screened and integrated TB/TST/scabies/HepB activity, no manual placeholders) and `full_project_interval` (default `"quarter"` - controls the granularity of the two full-project-history outputs, `out_tab_lep_ind_time()` and the treatment-proportions plot/table, which are NOT scoped to the reporting period). Renders in landscape (`reference-doc: landscape_reference.docx`) to accommodate the wide quarterly leprosy-indicators table.

## Environment Setup: renv and Dual-IDE Support (RStudio + Positron)
* **`.Rprofile` is IDE-agnostic and base-R only.** It creates the expected directory structure and bootstraps `renv` via `source("renv/activate.R")`, then prints a welcome message. It does **not** use RStudio's `.First()` convention — Positron does not call `.First()` automatically the way RStudio does, so all startup logic runs as top-level statements executed directly when `.Rprofile` is sourced. Because no packages (including tidyverse) are loaded yet at this point, `.Rprofile` must only use base R (e.g. `lapply()`, `function()`, `file.path()`) — no `purrr`/pipe-from-tidyverse syntax.
* **`PEARL.Rproj`** is RStudio-specific and is safely ignored by Positron (Positron has no equivalent file and instead treats the opened folder as a VS Code-style workspace). Keep this file in the repo for RStudio users and for tools like `here`/`rprojroot` that treat it as a project-root marker — no harm in Positron.
* **Workspace files:** `RestoreWorkspace: Never` and `SaveWorkspace: Never` are set in `PEARL.Rproj` to prevent `.RData`/`.RDataTmp*` regeneration.
* **`.posit/` folder:** Positron creates a local `.posit/assistant/` folder (Assistant settings and saved plans). This is user/IDE-specific and is excluded via `.gitignore`.
* **renv bootstrap:** First run of `.Rprofile` in a new clone triggers `renv/activate.R`, which downloads and installs the pinned renv version (currently 1.2.3) into `renv/library/<platform>/<R version>/`, then restores packages per `renv.lock` (R 4.5.2, CRAN mirror: `mirror.aarnet.edu.au`). Verify with `renv::status()` after first bootstrap.
